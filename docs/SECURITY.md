# Безопасность MeshPilot

## Модель угроз

MeshPilot — локальное десктопное приложение с доступом к чувствительным данным машины
(файловая система, конфигурация сети, ключи API). Основные риски, на которые мы проектируемся:

1. **Компрометация через «умный» LLM**: модель предлагает опасное действие / «выполняет» его текстом.
2. **Случайное разрушение данных** при очистке (удаление не-кэша).
3. **Утечка секретов** (API-ключи) в историю, логи, экспорт, сеть.
4. **Эскалация привилегий** (root) без ведома пользователя.
5. **Подмена зависимостей / цепочка поставки**.
6. **Утечка сетевой активности** без явного действия пользователя.

## Что мы делаем

### Секреты
- Ключи Groq/OpenRouter сохраняются только в системном кольце Secret Service
  (`keyring`, service `meshpilot`). При недоступности кольца — **только память процесса**
  (session fallback), с явным предупреждением в UI. На диск никогда.
- Кольцо/сессия читаются только в момент вызова (тест подключения, чат, список моделей).
- Экспорт настроек (JSON) **не содержит ключей**; сброс настроек **не удаляет** ключи
  (это отдельная операция «Удалить ключ»).
- История чата — atomic rename с `0600`; битый файл переименовывается в `*.broken.json`, не удаляется молча.
- Ошибки провайдеров нормализуются до безопасных строк (статус + сообщение провайдера ≤300 символов);
  ключ не логируется и не попадает в ответы IPC.

### Разрушительные действия
- Все деструктивные операции требуют явного подтверждения в UI (confirm modal) и флага `confirmRisky` для risky/opt-in категорий.
- `safeProfileOnly=true` по умолчанию: без явной галочки очищаются только `safe`-категории.
- Прямые удаления — строго внутри канонизированного `$HOME`; симлинки не раскрываются;
  корзина и только её подкаталоги (`files`, `info`, `expunged`);
  системные пути — исключительно через `sudo -n` (неинтерактивно).
- Никогда не удаляем: профили браузеров, историю/пароли/куки, данные мессенджеров (только кэш),
  документы, конфиги, `/var/lib`, чужие home-каталоги.
- `dryRun` — полный проход без удаления.
- Повторный анализ после применения — пользователь видит фактический результат.

### Системные изменения
- Зеркала pacman: бэкап текущего mirrorlist в `~/.local/state/meshpilot/backups/` перед
  любой записью; запись только при ≥3 валидных серверах от ранжировщика; при ошибке tee — бэкап остаётся.
- DNS: применение только в systemd-resolved (drop-in `50-meshpilot.conf` + restart) или в статический
  `/etc/resolv.conf` (не symlink). NetworkManager — явный отказ с пояснением (поддержка позже).
  Всегда создаётся бэкап; `dns_rollback` восстанавливает.
- Обход (byedpi/zapret): локальный прокси **только на 127.0.0.1**, unit `meshpilot-byedpi.service`
  в user systemd, никакого DNAT/iptables/ TUN, никаких удалённых серверов. Трафик уходит только
  на указанные вами URL и только по кнопке «Проверить».
- Расписания: systemd user timers, режим **report-only**; код, который запускается по таймеру, —
  read-only отчёты в `~/.local/state/meshpilot/reports/`.

### Привилегии
- Приложению **не нужен root** для: телеметрии, очистки пользовательских кэшей, трафа обхода,
  расписаний, чата, настроек.
- Root нужен только для: `paccache`, vacuum journald, coredumps, mirrorlist, DNS drop-in —
  и только через `sudo -n` (NOPASSWD или helper). Без sudo -n соответствующие действия
  честно помечаются `needs-helper` и не выполняются.
- Никогда не запрашиваем пароль в UI, не просим «ввести пароль для sudo», не используем `pkexec` с пользовательским вводом.

### LLM и контент
- Инструменты модели: read-only (`get_snapshot`, `cleanup_analyze`, `dns_status`, `mirrors_status`) и навигация (`open_section` с enum).
  **Нет** инструментов записи/удаления: модель не может «применить» DNS, «очистить» диск или «включить обход».
- System prompt фиксирует эти ограничения; нарушение enum → вызов отклоняется.
- Пользовательский контент не отправляется никуда, кроме выбранного провайдера (Groq/OpenRouter) и только по явной отправке сообщения.

### IPC / веб-view
- CSP: `default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline'; img-src 'self' data:; connect-src 'self' ipc: http://ipc.localhost; object-src 'none'; base-uri 'none'; form-action 'none'`.
- Capabilities: только `core:default` (нет fs/shell/process/http плагинов).
- Все ответы IPC — сериализуемые DTO; `AppError {code, message}` — без путей к системным файлам сверх необходимого, без ключей.
- Демо-режим (вне Tauri) — визуально отличим (бейдж, баннер), никаких «тихих» применений.

### Цепочка поставки
- Зависимости: Tauri 2 (pin `=2.12.7` / `tauri-build =2.7.6`), React 18, Vite 5 — минимальный набор;
  `reqwest` с `rustls` (OpenSSL не требуется); `keyring` (Secret Service).
- JS: lockfile `package-lock.json` коммитится; `npm ci` в CI.
- Rust: `Cargo.lock` пока не сгенерирован (нет доступа к crates.io на рабочей машине) —
  будет закоммичен первым `cargo build` на CachyOS; до этого CI собирает с плавающими минорными версиями (см. PROJECT_STATE.md).
- CI: actions pinned по SHA; `permissions: contents: read`; одноразовые runner; секреты в CI не используются.

## Известные ограничения и открытые вопросы

- **Helper** (polkit-based, узкий список действий) — не реализован; `needs-helper` — честная заглушка.
- `sudo -n` зависит от конфигурации sudoers пользователя; без NOPASSWD привилегированные
  действия недоступны (осознанное решение: лучше отчёт, чем висящий диалог).
- `byedpi`-стратегии подобраны под типичные случаи DPI; не гарантируют работоспособность — UI показывает «works по N URL».
- `dns_benchmark` использует plaintext UDP/53 без EDNS — отражает базовую достижимость, не качество DoH/DoT.
- AWS-LC (rustls) может потребовать `cmake` при сборке на «голой» системе (см. README → pacman -S cmake).
- CachyOS VM smoke-тесты (из PR #1) к этой ветке не подключены.
- Автообновление — отсутствует (запланировано через Tauri updater + подпись, этап 3).
